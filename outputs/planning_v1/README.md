# outputs/planning_v1

Small committed outputs of the planning overlay (restructuring plan v2, section 3.1). On 3 October 2026 this folder holds only the receipts of the engineering runs made for protocol v1b, including the run of record of the corridor and the E4 build of record. Protocol v1b is **not signed**: no FPPS, no A–E class and no ensemble has been computed, and no file here holds a value for a single tambon. The owners answered every owner choice on 3 October 2026 (decision log R12); the status column says which receipt that turned into evidence of record. A review the same day reopened OI-04 and OI-06 of protocol v1b: the join log and the facility counts of the run of record were measured by the E0 spike, and those two items take their values from task E4 (owner-choices entry 1, plan row G7b). In R13 the owners chose to wait for E4 (entry 24, option A); the E4 build of record reproduced the spike's values exactly, and both items closed from it. A file written before R12 is not rewritten, so its own `status` field may still say `candidate`; protocol v1b says what it is now. The planning-frame build of 3 October names tambons, so its receipt sits beside the frames in `resources/planning_frames/`, not here.

**Every file** carries `generated_at_utc`, `source_timestamp`, `confidence_class` (always `low`), `confidence_basis`, `assumptions`, `official_warning: false` and `operational_status: non_operational`. In a JSON file they are at the top level; in a GeoJSON file they are in the feature's properties. A candidate file also carries `status: candidate` inside the file, and a file of the run of record carries `status: of_record` (`log_of_record` for the join log, `run_of_record` for the receipt), so a copy taken out of this folder still says what it is. `tests/test_planning_v1_outputs.py` checks all of this for every file here. None of these outputs is an official warning or an observation of a flood.

**Task E4** (`scripts/build_planning_context.py`, rules in `src/floodguard/planning_context.py`) exists since 3 October 2026. Its build of record for Mae Sai in vehicle mode was made on 3 October 2026 in a compute window the agent declared under R13, and wrote the two files listed above: `e4_planning_context_se1_vehicle.json` (the receipt: input hashes, context hash, grade-join summary, facility counts, plan-row acceptance and the comparison with `corridor_polygon.run_of_record.e4_reproduction_check`, plus a `run` section with the compute window, times and memory) and `grade_join_log_e4_se1_vehicle.json` (its join log, status `log_of_record`). The facility table and the context hold DDPM rows (pitch level), so they stay outside Git under `<external_data_workspace>/proposal_execution/planning_v1/<case>/e4_<mode>/`; a candidate build writes all its files there and nothing here. `--verify` rebuilds into a temporary folder and compares byte for byte the join log, the facility table, the receipt without its `run` section and the retained context, whose build time (`generated_at`) alone is left out. The first three `--verify` runs of the build of record, made before a review on 3 October 2026, checked the retained context only through the hash written at its end; the fourth compared it in full and found it the same (`corridor_polygon.e4_build_of_record.verify` in v1b). A build of record cites decision log R13 for its compute window only if it is the first se1 vehicle build of record; any other records the decision-log entry passed with `--window-authority`, or that its window awaits owner acceptance.

Each spike file carries its generation time, so its SHA-256 changes from run to run. To compare two runs, use the hashes of the content alone: `geometry_sha256` in a corridor file, `joins_sha256` in a join log and `context.canonical_sha256` in a spike receipt. The `reproducibility` block of a spike receipt does that comparison against the run before it.

The inputs are read-only files outside Git. Their locations are arguments of each script, and their SHA-256 values are in each receipt. The owner decisions are in `docs/proposal_execution/planning_protocol_v1b_owner_choices.md`, answered on 3 October 2026 as recommended (decision log R12).

## Runs made after protocol v1b came into force

Protocol v1b was signed on 3 October 2026 and is in force since its SHA-256 was recorded in `docs/proposal_execution/RECEIPTS.jsonl` (06:27:58Z). It is not edited again, so it cannot list a later run. Every run made after that time writes its own receipt here, and the receipt names the SHA-256 of both protocol files (`tests/test_planning_protocol.py` checks that). The files below carry the same fields as every other file in this folder and name no tambon.

The whole ranking table gives the tambon of every ranked link (drafter reading DR-B06: the tambon that holds the midpoint of the edge), so it is not written here. It is a function of the inputs: `scripts/build_critical_links.py --write-ranking <path outside Git>` writes its bytes, and `--verify` recomputes the top-20 file, the receipt without its `run` section and the table's SHA-256 and compares them. The run reads no flood layer and computes no closure, no reroute, no access loss, no FPPS, no A-E class and no ensemble.

The first run was made on 4 October 2026 (generated 08:24:35Z, 7 seconds) and is the only run that wrote anything. `--verify` was run once after it (08:25Z) and recomputed the same bytes. What it measured, for the whole frame: 26,130 of the 65,673 baseline edges (65,328 road edges and 345 grade-join connectors) carry a baseline route; 99.6% of the residents with a route reach a main-road entry before a hospital, so trunk and primary edges carry no flow and are not ranked; the 20 highest-ranked links are 20 consecutive edges of one tertiary street (OSM way 1114870832), with 8,722 to 9,261 residents each, and none of them is a graph bridge; the top 200 lie on five OSM ways and include two grade-join connectors (ranks 163 and 164). The protocol ranks edges, not streets, and does not say whether a connector can be a critical link (`open_points` in the receipt).
