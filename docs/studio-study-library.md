# Studio study library

Studio separates measured research, model applications, planning qualification and historical experiments. The website displays saved evidence. It does not train models, acquire imagery, or promote research outputs into decisions.

## Pages and ownership

| Route | Evidence owner | Scope |
| --- | --- | --- |
| `/studio/` | Study catalogue | Choose a study; no global model leaderboard or borrowed planning status |
| `/studio/planning-evidence/` | Existing Mae Sai evidence context | Qualification, restricted model registry, governance and authorization |
| `/studio/archive/mae-sai-geoai/` | Historical `2026-07-30-r1` report | Original optical/teacher experiments and earlier research; distillation fidelity is not water accuracy |
| `/studio/studies/c2s-ms-20260915/` | C2S-MS `r1` | Original-chip public benchmark overview |
| `…/data/` | Same C2S revision | All event assignments, observation dates, source licences and geographic context |
| `…/models/` | Selected frozen model/input version | Fitting, features, calibration, abstention and recorded TreeSHAP |
| `…/results/` | Original C2S chips | Raw/calibrated, pooled/per-event, full-valid/selective scores with support |
| `…/rtc/` | Separate matched RTC record | 46 chips, two events, fixed-ramp comparison and transfer limitations |
| `…/explorer/` | C2S human labels and frozen predictions | All 111 test chips; six trained model/input combinations |
| `…/files/` | Source receipts and public projections | Downloadable JSON evidence, attribution, checksums and reproduction limits |
| `…/mae-sai/` | Separate Mae Sai inference record | Six model/input versions, four layers, pre/post radar, checkpoint lineage; no local accuracy metrics |
| `/studio/cases/mae-sai-2024/` | Mae Sai 2024 timeline manifest (`TIMELINE_MANIFEST_URL`) | Hour-by-hour replay of a low-confidence terrain-model reconstruction with dated Sentinel imagery, VIIRS daily flood maps and HII hourly rain; the water is modelled, the VIIRS maps and rain are observed |

Each C2S section has its own static route. Query parameters record model/input, calibration state, event/chip, map layer and overlay selections. Invalid selections or revisions display an unavailable state. Ordinary browser Back and refresh preserve the selection.

## Frozen public projection

`apps/web/public/studies/c2s-ms-20260915/r1/manifest.json` binds the summary and all report/index assets by exact byte length and SHA-256. Its reviewed digest is pinned in `apps/web/src/lib/study-report-release.ts`; the browser does not trust a digest downloaded alongside an unchecked manifest. JSON loads validate study/revision, schemas, safety flags, partition roles, metric support and inference restrictions. Missing, altered, wrongly scoped or redirected evidence fails closed.

The records are independent of `useFloodGuardData` and the existing Mae Sai model registry. No C2S metric is inserted into a blocked Thai evaluation. Separate original-chip, RTC and Mae Sai records retain checkpoint lineage. Source hashes and public-projection hashes are separate because downloads are reserialized and private experiment-root paths are made relative.

The source experiment checkout was `codex/public-flood-models` at `36e2536d9dee68c7747e1755e508893858fd9a69`. Reproduction requires that experiment's archived reports and acquired work data, including its frozen checkpoints. Those large local inputs are not supplied by this frontend branch, and there is no published checkpoint download. The website documents this limit and links public dataset acquisition sources.

### Visual evidence

- All 111 test chips: 65 Australian, 18 Nigerian and 28 Pakistani chips.
- Six combinations: RF, XGBoost and U-Net, each with SAR-only and context inputs.
- 633 combinations with valid inputs; 33 explicitly unavailable combinations from 11 context-empty chips.
- 2,147 small PNG previews, including 26 Mae Sai previews. Full rasters and weights remain outside Git.
- Each available case has radar/reference, calibrated probability, binary prediction and error views. Preview dimensions are at most 256 pixels; benchmark counts use the original full-resolution valid pixels.
- Export verification replayed all 633 available cases from frozen checkpoints. Every TP/FP/FN/TN count matched the archived report exactly. This checks correspondence with the saved C2S evaluation; it does not establish Mae Sai accuracy.
- Mae Sai probability and entropy remain inspectable in abstained areas. The optional tint and separate abstention map disclose the screening result; neither creates a new accepted prediction or reference label.

The visual index itself is checksummed through the manifest. PNGs carry embedded provenance and individual digests in that index. `export_study_visuals.py` verifies all source/checkpoint receipts and the full-resolution confusion counts before publishing a completed index.

`.gitattributes` preserves `/studies/` files byte-for-byte, including the original newline style of independently exported indexes. The integrity check also compares working files with their Git blobs, so a locally passing manifest cannot become invalid after a clean checkout.

### Geographic context

The event map uses the recorded bounding-box centres and Natural Earth 1:110m country outlines. The outlines are [public domain](https://www.naturalearthdata.com/about/terms-of-use/). They are display context, not model features or labels. Country labels inferred by point-in-polygon lookup are marked accordingly; a centre does not describe every chip or establish an event boundary. Source URL, downloaded bytes, SHA-256, verification time and transformation assumptions are saved in `geography.json`.

### Case replay: links, exports and offline copy

The replay's data revision is chosen only by `TIMELINE_MANIFEST_URL` in `apps/web/src/lib/flood-timeline.ts`; the page, the offline inventory (`apps/web/scripts/case-replay-inventory.mjs`), the integrity check and the tests derive every asset from that manifest.

- The page serves revision `r4`, which replaced `r3` (removed from the tree: one revision ships, and an old link to an earlier one no longer resolves). r4 keeps r3's model and figures and adds the evidence fields described below. Since r3 the bake includes the east Copernicus DEM tile (N20E100), so the model covers the whole district (305.6 of 305.6 km²), every road and candidate facility is modelled, and every shelter candidate lies inside the replay grid (the bake reads OpenStreetMap straight from the Geofabrik extract, cut to the replay area; the four candidates outside the grid that an older, wider cached cut had carried are gone, 113 candidates instead of 117, with the same 95 eligible sites and the same ranked plan); the impact card then says the district is fully modelled instead of naming unmodelled land. Its HAND raster is RGB: R is the effective HAND code and G the per-cell depth factor k × 255, so depth is k × (stage − HAND) while wetness depends on the code alone. Roads and facilities carry the same k: a road is impassable when the rounded k × (stage − h) reaches 0.3 m and wet when that rounded depth is above 0, the same rule as `floodguard.flood_timeline.road_state`; a Python-generated fixture (`apps/web/scripts/road-state-parity-fixture.py`) checks every hour of the replay grid. The stage is the assumed Sai main-stem stage at the Mae Sai bridges; tributary cells rise k × stage (the page says "a fraction of this level", because k on the page means the plan size). The stage curve interpolates over every anchor, including 10 Sep 18:15 (0.1 m, GISTDA-anchored; GISTDA gives no time zone, so ICT is assumed — as UTC the knot would be 11 Sep 01:15 ICT) and 11 Sep 02:00 (2.5 m). Area, road, facility, people-in-water and access figures recomputed in the browser equal the manifest's baked keyframe statistics, and unit tests enforce this.
- Evidence fields (r4): `timeline.json` follows `packages/contracts/schemas/case-replay-timeline.schema.json`, and the bake refuses to write a manifest that breaks it or the rules in `floodguard.replay_manifest`. Besides the data, the manifest says what the data is: `generated_at`, `data_version`, `dataset_mode` (with `data_mode` kept as an alias), `operational_status` (`non_operational`), `confidence_class` (mirrors `confidence`), `confidence_basis`, `source_name`, `event_time`, `permitted_use` and `reason_blocked`. `accepted_fpps` and `accepted_action_class` are null and `protocol_sha256` is null with the reason `not_a_protocol_case` (D7): the replay computes no score and no action class. `evidence_blocks` gives every part of the manifest a lane, a tier, a temporal relation and its own source timestamp: the water reconstruction, residents in water, access and the shelter plan are `SCN` ("T1 scenario (model)"); the VIIRS maps, each Sentinel-1 and Sentinel-2 image and the rain record are `OBS`; GISTDA's 10 Sep figure, the UNOSAT 3991 size comparison and the 16 Sep Sentinel-1 size comparison are `CAL` (calibration); product 4009 is `SCN-ENV` (a season envelope, not shown); reported shelters and the chronology are `REP`. The three `model_*` fields that sit beside each VIIRS day are model output, so the VIIRS block lists them as `scenario_fields` ("T1 scenario (model)") and `viirs_daily.model_fields` says the same; they are not the agency's figures. The bake and a test fail when content has no lane: a new top-level block, a new item of a list that is covered item by item, or a new child of an object that is covered child by child (a new entry under `vectors`, for example). They also fail on any score or action-class field at any depth (`fpps`, `action_class`, `priority_score`); only the two null top-level `accepted_*` fields may carry those names. `exploratory_knowledge` states which external figures were used or known while the model was tuned: GISTDA's 9.9 km² was used on purpose to set the onset knot; the 16 Sep Sentinel-1 pass was used to re-tune the recession keyframes (best-fit stage 0.10 m); UNOSAT 3991's 70 km² was known during tuning; the product 4009 comparison was computed after the keyframes were final and was not used. The VIIRS comparison was not used for tuning either, but the manifest claims no more than the build history supports: it first appears in commit 129ff03 (29 Sep 2026), the same change that moved the 10 Sep 18:15 knot from 0.12 m to 0.1 m to follow GISTDA's figure, and the order of the two steps within that change is not recorded, so `known_during_tuning` is null for VIIRS (relation `not_used_for_tuning`) and the comparison is not presented as an independent check. Putu can settle the order; until then the wording stays as it is. The page's radar line therefore reads "Radar size comparison (Sentinel-1, 6 Sep → 16 Sep 06:16 ICT; calibration-informed, not an independent check)", and nothing on the replay is labelled an independent check. `publication_eligibility` lists a licence and terms per input (HII rain CC BY-NC, OpenStreetMap ODbL 1.0, WorldPop CC BY 4.0, COD-AB CC BY-IGO, VIIRS "No licence stated by the provider", Copernicus DEM and Sentinel under their own terms, and product 4009 CC BY-SA 4.0 marked "Not yet shown; rights record pending owner confirmation"; the bake reads that status, the reply quote and its relay date from the rights record, which is one of its inputs, so a confirmed record needs a new bake and the tests say so until it is done), and `input_sha256` repeats the input receipt's 32 hashes. OpenStreetMap is identified there by the Geofabrik PBF itself, never by a derived cache. The top-level `source_timestamp` now spans the dated event observations (Sentinel-2 on 5 Sep to the last rain hour on 19 Sep, which covers VIIRS to 18 Sep), and `source_timestamp_note` says which inputs are dated elsewhere. `sources` names both elevation tiles and WorldPop (the unconstrained `tha_ppp_2020` grid; r3 called it constrained). `generated_at` is a declared bake time (`--generated-at`, recorded in the receipt and carried by `--verify`), or the newest dated input when none was declared. A plain bake without the argument may carry the recorded time only when it reproduces every recorded output file; when any file differs it stops, writes nothing and asks for `--generated-at`, so the page never states a generation time that is no longer true; it is never read from the machine clock, so a rebuild gives the same bytes. `git_commit` is null with a reason: a file cannot hold the hash of the commit that adds it, so the receipt identifies the bake sources by SHA-256 and `git log -1 -- <path>` names the commit. On the page, "How to read these numbers" states "Status: non-operational" and when the data files were generated; "Sources, assumptions and limits" adds "Licence per input" with the conditions of use, "What was known when the model was tuned", and the status and generation time in its footer, all in English and Thai. `parseTimelineManifest` reads both the r4 shape and the r3 shape that a client may still hold in its offline copy (a unit test uses a trimmed r3 fixture), fills the defaults r3 implies, and refuses a manifest that is not marked "not an official warning", or that claims an operational status or an accepted score or class.
- Sentinel-2 scaling (r4): the Earth Search L2A files on disk already have the processing-baseline 04.00 offset removed (in the replay area 75% of the valid red values on 5 Sep and 48% on 15 Sep are below 1000, and red over dense vegetation has a median near 310–320, which would be negative reflectance otherwise), so reflectance is DN / 10000 (`floodguard.flood_timeline.sentinel2_l2a_reflectance`, with a unit test) and the bake no longer subtracts 1000. The display stretch keeps the same cloud cut (DN 3500, now written as reflectance 0.35), so the pictures stay the same: the 15 Sep image is byte-identical to r3, and the 5 Sep image differs in 43 of 13.2 million channel values by one level before encoding (713,848 bytes against 713,912). The other 19 data files are byte-identical to r3; only `timeline.json` grew (196,294 bytes in r3; 220,494 in r4 as baked on 2 Oct 2026, 07:24 ICT).
- Layout: a short hero (title, one-line lead, the disclaimer and a collapsed "How to read these numbers" box with confidence, timestamps, a link to the assumptions and a glossary of stage, HAND, low-confidence water, road nodes, T1 scenario and freeboard) is followed directly by Play ("Play 9 → 19 Sep (26 s)"), the time readout and a "Map layers" button above the map; their height is reserved from the first render, so nothing that loads later moves the map. The Play button reserves the width of its widest label (its `data-labels` attribute lists them all), so Play to Pause changes nothing around it; on phones the bar is a fixed grid (Play and "Map layers", then the moment, then two reserved lines for the summary), so no label or replay hour moves the map. The time readout is never cut: at the narrow end of the two-column layout (1081 to 1239 px, a 1366 px laptop at 125%) the cards column narrows to as little as 300 px and the bar tightens, so that Play, the whole readout and "Map layers" fit on one row, and the study smoke measures every replay hour in both languages at 1081, 1100 and 1240 px, with room to spare for a scrollbar. Imagery, comparison, water and road modes, water opacity and the layer switches sit in the "Map layers" drawer over the map: opening it moves keyboard focus into it (the next Tab reaches its first control), and Escape or "Close" hands focus back to the button. Escape also closes the drawer from anywhere else in the map-and-timeline section (Play, the legend, the map, the slider), leaving focus where the reader is. A compact legend for the active water and road modes (and any switched-on scenario or observed layer) sits on the map under the zoom control, with the marker key folded inside it; it starts collapsed on phones. The legend always names the view the map draws: a resident view that is still waiting for its raster (or could not load it) is drawn as water depth, and the legend shows the depth key with a sentence saying so (`drawnWaterMode` in `flood-timeline-water.ts` decides this for the map, the legend and the exports). On desktop the map column is sticky beside the cards, so a card's "Show on map", k slider or shelter-set switch changes a map that stays in view; on phones a one-line summary of the moment sits under the readout. Technical terms carry a hover or focus definition from the same glossary; Escape closes it without moving the pointer or the focus, and the box is shifted sideways so it stays inside the viewport (360 px included).
- Low-confidence water (r3 on): the HAND raster's B channel is 255 on filled pits and dead-flat ground less than 0.1 m above its channel, which reads as wet at almost any stage. The page decodes it only when the manifest declares `hand.low_confidence_channel` ("B"); wet flagged cells are then drawn paler and desaturated with a diagonal hatch in every view that draws water (depth, first flooded, hours under water and people in flood water; "All residents" draws no water), on the map and in the PNG and video exports, with a legend entry ("Low-confidence water: flat or filled low ground in the elevation model") in both. The key beside that entry is drawn in the colours the map gives those cells in the view on screen (`lowConfidenceKey`, built on the same `lowConfidenceRgba`): blue in the depth view, purple-grey in the first-flooded and hours-under-water views. Without the hatch, flagged cells in the first-flooded and hours-under-water views would read as "flooded first and longest". One paint plan (`waterPaintPlan`) serves the map and the exports, so they hatch the same cells. The evidence card gives the manifest's share (14.0 of the 88.7 km² wet at the modelled peak) and meaning. The figures themselves are unchanged: flagged cells still count as wet.
- Imagery: the 15 Sep Sentinel-2 image is the first clear optical view after the flood; while it is on screen the map, the "This moment" card and the evidence say that its brown areas are mud left by the floodwater (observed). The caption beside the readout always names the image at the playhead (the old fixed "pre-event images" line is gone), and "Hours under water" uses a yellow-green-blue-purple ramp without browns so it never reads as that mud.
- Water can show depth at the moment, the first flooded hour, hours under water, people in flood water (wet cells coloured by WorldPop 2020 residents per hectare) or all residents. Arrival and duration are pure functions of the assumed stage curve sampled at the start of each local hour (9 Sep 00:00 to 19 Sep 23:00); road-cut hours use the same grid and the same 0.3 m threshold as the road state. WorldPop is modelled residential population, not the 2024 population or border-market visitors.
- Evacuation access is a T1 scenario, not observed outcomes. It covers residents at road nodes who can walk to an open, dry shelter within 2 km on roads that are still passable. The shelter set is either the sites reported in use in September 2024 or the first k sites of the ranked plan (k = 1 … N, default the smallest plan that reaches 90% of the most any plan can reach). The card first puts the two shelter sets side by side (roadmap P2-4): the reported set and the first k sites of the plan, each in its own table with two columns, all residents at road nodes and residents whose home node floods at the modelled peak (the builder's `home_wet` rule on `home_code` at `shelters.method.peak_stage_m`; their sum equals the plan's `demand_people`). The rows are, in this order: residents with a shelter of the set within reach before the flood; residents who still have one at the replay hour; residents newly lost, out of that set's own baseline, with the share; and the modelled access cut-off hour, the first replay hour when fewer than half of the baseline residents still have access (or "not reached in this replay"). No headline figure ranks the sets and none is drawn in an alert colour. At the 3.5 m peak the reported set has 34,525 residents within reach before the flood and 7,086 newly lost (21%), against 24,910 and 13,429 (54%) for the plan of 8; among residents whose homes flood it is 5,698 (299 keep access) against 7,580 (460 keep access), so each set is ahead on one way of counting. Because the plan is built for evacuating before the water rises, its table leads with the cut-off hour, and a note says that its loss at the peak counts residents who are still at home by then and does not grade the choice of sites. The hours carry the label "Hours from illustrative stage keyframes, not observed". The same figures come from `floodguard.shelter_set_comparison.shelter_set_summary` in Python and `shelterSetComparison` in the browser. A population scope then says whose access the equity gap, the subdistrict bars, the chart and the map count: by default the residents whose homes flood, or all residents at road nodes; one muted line gives the residents of that scope without a dry shelter (lost because of the flood, and already out of reach before it). The node file (`access-nodes.bin`, little-endian columns per the manifest layout) is reduced once per set and scope to cumulative histograms by cut level, so each hour costs O(1). The Evacuation Equity Gap follows the replay's own rule, `evacuationEquityGap` in the browser and its twin `floodguard.replay_equity.replay_equity_gap` (`floodguard.equity` is unchanged, plan section 5.6): rates, ratio and band limits are those of `floodguard.equity`, but no ratio is given, with a reason, when a group has fewer than 50 residents (`insufficient_group_denominator`, checked first), when nobody has lost access (`no_loss`; `floodguard.equity` would say 1.0), or when only proxy-vulnerable residents have (`undefined_ratio`). The page then prints "no ratio shown" and says why in one sentence. With a ratio it prints two decimals and a plain comparison ("Proxy-vulnerable residents are about 3.9× less likely to lose access (4.47% vs 17.56%)"); it never prints "0.00": when no proxy-vulnerable resident has lost access it says so in words (in Thai "ไม่มีผู้ใด…", not "ยังไม่มี", which would read as "not yet"). Under it the card gives both denominators of each group (all residents counted, and those with a shelter within reach before the flood) and one line on why the proxy points the way it does here (hillside and remote homes stay dry). Each rate divides by all residents counted in the group; with the within-reach denominator the plan of 8 would read 320 of 373 against 13,109 of 24,537, which is why both are shown. "Vulnerable" there is the terrain/remoteness proxy, not demographic vulnerability. The "people cut off" layer draws the scoped nodes that have lost access as population-weighted blobs on a canvas overlay.
- Shelters: reported 2024 sites are stars with sourced popups and a model check at the modelled peak, and unlocated sites are listed without a pin. The Mae Sai District Office (R05) is drawn as a relief and command site (diamond), not a shelter, and Wat Mueang Daeng (R04) is labelled a shelter only from 21 Sep, following the research notes (`REPORTED_SITE_ROLES`, tied to the manifest wording by a unit test). Plan candidates appear as numbered top-k badges, eligible rings and grey ineligible markers with reasons; candidates off the DEM tile (east of 100°E) or off the grid are drawn as not modelled instead of showing the build's placeholder high-ground or flood results (r4 has none: its OpenStreetMap cut ends at the replay grid). A collapsible "Other shelter candidates" card lists every ring and dot with its reasons and a "Show on map" button, so none is pointer-only. Popups give the capacity estimate with its Sphere basis and the load for the chosen k. Both plan-size sliders share the label "Plan size k = N" and a sentence that updates with the slider ("k = 3: 3 sites cover 5,725 of 14,169 residents whose homes flood (40%) · late evacuation 23%"); the coverage curve has a y-axis title and shows the ranking as a range, and the uncoverable residents are called out as the shelter gap. - Capacity-aware view of the shelter plan (roadmap P2-9; T1 scenario, model). The coverage ranking counts who can walk to a site, not who fits inside, so the plan card adds a block "If capacity counts: who fits (two bounds)" below the plan list. Every resident of a home that floods at the modelled peak (14,169, the plan's `demand_people`) is assigned to an eligible site within the 2 km walk without going over that site's capacity estimate (`floodguard.evacuation_access.capacitated_assignment`, a maximum flow in thousandths of a resident; pytest cross-checks it against a networkx min-cost flow). Two bounds use the same sites: in the lower bound a site without a capacity estimate holds nobody, in the upper bound it holds the median estimate of its site kind (schools 253, places of worship 76, government offices 81; no community centre has an estimate, so those take the median of every estimate, 80). The table gives residents who fit and overflow (demand − fit) for four site sets: the first k sites of the plan above (for the default k = 8: 495 to 1,057 fit of the 7,580 within the walk), the first k sites of the capacity-aware ranking (1,805 to 2,441), all 25 sites of that ranking (2,366 to 3,900) and every one of the 95 eligible candidates (2,673 to 4,149, so at least 10,020 of the 14,169 have no place under these estimates). The capacity-aware ranking (`capacitated_plan`) adds, at each step, the site where the most additional residents fit under the upper bound and ends at 30 sites or when the next site adds less than 0.5% of demand; its plans are nested and each site's load is the number it adds when it joins. A note names the plan sites that the nearest-site rule gives more residents than their estimate holds (three of the default eight; the largest gap is a place of worship with about 79 places carrying about 2,430 residents, 31 times the estimate). The block ends with five standing caveats, in English and Thai: T1 scenario (model); demand is every resident of a home that floods at the peak, an upper bound because many people stay with relatives; capacity is an unverified footprint estimate (53 of the 95 eligible candidates have no footprint); the sites are candidates to verify, not a list of sites to open; and the planning overlay's listed-capacity figures come from a different source. The manifest block is `shelters.capacitated` (whole residents; `capacity_basis` is "OSM footprint x 0.5 / 3.5 m2 (Sphere), unverified" or "unknown"), with its own evidence block `capacity_aware_plan`, confidence, source timestamp and assumptions. The page only reads those figures (`capacityAwareView`); a manifest without the block shows the card as before. No participation sweep and no listed capacity from another source is in any public file.
- What-if levels and the robust core (roadmap C-1; T1 scenario, model). Because the 3.5 m peak is illustrative, the bake repeats the candidate screening and the coverage ranking with the peak at 2.5 m and 4.0 m (`shelters.robustness`, evidence block `plan_robustness`): residents whose homes flood are 10,333, 14,169 and 16,069, and 95, 95 and 94 candidates stay eligible. Within each level the plans are nested. The card shows the three levels under the label "What-if levels around an illustrative peak, not return periods" and marks, on the plan list, the sites that are among the first k at every level ("Robust core"; 5 of the default 8). A site in the robust core is still a candidate to verify.
- Export pack for spreadsheet and GIS users (roadmap P3-1; T1 scenario, model). District and DDPM staff work in spreadsheets and GIS, so the bake writes eight download files into `r4/exports/` (`floodguard.replay_exports`, pure writers with pytest): `shelter_plan_reported_2024.csv` (the 19 sites reported in use, with a model check in columns that start with `modelled_`), `shelter_plan_k.csv` (the coverage ranking, sites 1 to 12), `shelter_plan_capacitated.csv` (the capacity-aware ranking, 25 sites under both bounds), `shelter_sites.geojson` (113 candidates and the 15 located reported sites as points), `modelled_road_inundation_by_hour.csv` (one row per OpenStreetMap way of the classes the replay models: 3,478 ways with `road_id`, `road_name`, `road_class` and `bridge_flag` from `outputs/mae_sai_road_risk.geojson`, the first replay hour at which the way is impassable and the first hour it is passable again; 613 ways are impassable at some hour, the first at hour 44, 10 Sep 20:00, and all are passable again by hour 153, 15 Sep 09:00), `modelled_access_loss_by_hour.csv` (one row per subdistrict and replay hour, 2,112 rows: residents with a shelter within reach before the flood and residents who have lost it, for the reported set and for the first 8 plan sites, each against its own baseline), `shelter_candidate_verification_sheet.csv` (next item) and `README_licences.txt`. The legacy candidate columns of the road file (`road_disruption_probability_0_1`, `candidate_status`, `confidence_class`, from the superseded Sentinel-1 change heuristic) are not carried, and the bake stops if a road piece the page leaves out would be impassable. No table is named as a timetable or a plan of closures: the tables are modelled road inundation and modelled access loss, and the wording lint reads every header.
  - Header: every CSV starts with provenance lines (first cell starts with `#`, the second line gives their number) and then one column header whose cells are the English key with the Thai label in brackets. The lines carry the title, the standing sentence ("T1 scenario (model) replay of a reconstructed 2024 event for preparedness planning and exercises; illustrative stage keyframes; not a forecast, not an observed closure record, not an official warning; non_operational; accepted_* null"), `operational_status`, `confidence_class` (low) with its reason, the lanes, `source_timestamp`, `generated_at`, the licence with attributions, what is not included, the assumptions (each in English and Thai), a pointer to the input receipt with one hash over all its rows (`input_set_sha256`), the SHA-256 of the file's direct inputs, and why `git_commit` is null. The provenance sits in the file, not in a sidecar: a sidecar is lost when a table is forwarded on its own, and the risk of this pack is a modelled table read as an operational record. Excel and LibreOffice open the files as they are (the lines show as rows above the header); QGIS and pandas skip the stated number of lines. The GeoJSON layer cannot hold comments, so it carries the same fields in a top-level `metadata` member before the features. CSV files are UTF-8 with a byte-order mark, so the Thai text opens correctly in Excel, and all files use LF line ends. A text cell that a spreadsheet would run as a formula is written with a leading apostrophe.
  - Licences: one lineage per file. Every file is OpenStreetMap-derived and stays under ODbL 1.0 with attribution; the other inputs (Copernicus DEM, WorldPop, COD-AB boundaries, the reported-shelter facts) are attribution-only. `floodguard.replay_exports.licence_problems` refuses a file that would also draw on a CC BY-SA source, a non-commercial one, a source without a stated licence or product 4009, and the schema allows only those five source ids. ## Reproduction and maintenance

From the repository root, with the original experiment data available:

```powershell
# Explicit inputs: an experiment checkout and a separate staging checkout.
python services/geoai-runner/scripts/export_study_visuals.py --source-root <experiment-checkout> --output-root <staging-checkout> --device cuda

# Optional explicit network acquisition for cartographic display only.
# Use the committed r1 summary as the event inventory; output must be new.
python services/geoai-runner/scripts/acquire_study_geography.py --summary apps/web/public/studies/c2s-ms-20260915/r1/summary.json --output <staging-checkout>/apps/web/public/studies/c2s-ms-20260915/r1/geography.json

# Assemble report projections after the visual index and geography exist.
python services/geoai-runner/scripts/export_studio_study.py --experiment-root <experiment-checkout> --output <staging-checkout>/apps/web/public/studies/c2s-ms-20260915/r1

# Validate/reproduce the committed historical projection from its original sources.
node apps/web/scripts/archive-historical-study.mjs
```

The report and historical exporters reject conflicting bytes in an existing revision. Acquisition refuses to overwrite an existing projection. A newly acquired cartographic file has a new verification timestamp; to reproduce the exact r1 bytes, reuse its committed `geography.json`. Future scientific runs require a new study/revision and reviewed manifest pin. Do not update September 15 metrics in place or use the already observed final test for tuning.
