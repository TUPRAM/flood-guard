# outputs/planning_v1

Small committed outputs of the planning overlay (restructuring plan v2, section 3.1). The first table lists the receipts of the engineering runs made for protocol v1b before it was signed, including the run of record of the corridor and the E4 build of record. None of those files holds an FPPS, an A–E class, an ensemble or a value for a single tambon. Protocol v1b was signed and recorded on 3 October 2026 (`docs/proposal_execution/RECEIPTS.jsonl`); the runs made since then are in the second table, under "Runs made with protocol v1b in force". The owners answered every owner choice on 3 October 2026 (decision log R12); the status column says which receipt that turned into evidence of record. A review the same day reopened OI-04 and OI-06 of protocol v1b: the join log and the facility counts of the run of record were measured by the E0 spike, and those two items take their values from task E4 (owner-choices entry 1, plan row G7b). In R13 the owners chose to wait for E4 (entry 24, option A); the E4 build of record reproduced the spike's values exactly, and both items closed from it. A file written before R12 is not rewritten, so its own `status` field may still say `candidate`; protocol v1b says what it is now. The planning-frame build of 3 October names tambons, so its receipt sits beside the frames in `resources/planning_frames/`, not here.

**Every file** carries `generated_at_utc`, `source_timestamp`, `confidence_class` (always `low`), `confidence_basis`, `assumptions`, `official_warning: false` and `operational_status: non_operational`. In a JSON file they are at the top level; in a GeoJSON file they are in the feature's properties. A candidate file also carries `status: candidate` inside the file, and a file of the run of record carries `status: of_record` (`log_of_record` for the join log, `run_of_record` for the receipt), so a copy taken out of this folder still says what it is. `tests/test_planning_v1_outputs.py` checks all of this for every file here. None of these outputs is an official warning or an observation of a flood.

**Task E4** (`scripts/build_planning_context.py`, rules in `src/floodguard/planning_context.py`) exists since 3 October 2026. Its build of record for Mae Sai in vehicle mode was made on 3 October 2026 in a compute window the agent declared under R13, and wrote the two files listed above: `e4_planning_context_se1_vehicle.json` (the receipt: input hashes, context hash, grade-join summary, facility counts, plan-row acceptance and the comparison with `corridor_polygon.run_of_record.e4_reproduction_check`, plus a `run` section with the compute window, times and memory) and `grade_join_log_e4_se1_vehicle.json` (its join log, status `log_of_record`). The facility table and the context hold DDPM rows (pitch level), so they stay outside Git under `<external_data_workspace>/proposal_execution/planning_v1/<case>/e4_<mode>/`; a candidate build writes all its files there and nothing here. `--verify` rebuilds into a temporary folder and compares byte for byte the join log, the facility table, the receipt without its `run` section and the retained context, whose build time (`generated_at`) alone is left out. The first three `--verify` runs of the build of record, made before a review on 3 October 2026, checked the retained context only through the hash written at its end; the fourth compared it in full and found it the same (`corridor_polygon.e4_build_of_record.verify` in v1b). A build of record cites decision log R13 for its compute window only if it is the first se1 vehicle build of record; any other records the decision-log entry passed with `--window-authority`, or that its window awaits owner acceptance.

Each spike file carries its generation time, so its SHA-256 changes from run to run. To compare two runs, use the hashes of the content alone: `geometry_sha256` in a corridor file, `joins_sha256` in a join log and `context.canonical_sha256` in a spike receipt. The `reproducibility` block of a spike receipt does that comparison against the run before it.

The inputs are read-only files outside Git. Their locations are arguments of each script, and their SHA-256 values are in each receipt. The owner decisions are in `docs/proposal_execution/planning_protocol_v1b_owner_choices.md`, answered on 3 October 2026 as recommended (decision log R12).

## Runs made with protocol v1b in force

Protocol v1b came into force when its SHA-256 was recorded in `docs/proposal_execution/RECEIPTS.jsonl` (3 October 2026, 06:27:58 UTC). The signed file is not edited again, so it cannot list a later run. Every run on real units made since then writes a receipt here instead: its inputs and outputs by SHA-256, its parameters, the SHA-256 of both protocol files (`protocol_sha256`) and the run times. These files may hold values for a single tambon. `tests/test_planning_v1_outputs.py` checks that each of them names both recorded protocol hashes and was written after the v1b receipt, and that every file written before it still names no tambon.

**How the shares were computed.** Counts are allocated to a tambon by the projected-area fraction of each 1 km cell inside it, as protocol v1b states for the national anchors (`national_vulnerability_anchors.method.allocation`, drafter reading DR-B04). The run uses the functions that produced the anchors (`floodguard.evidence_age_surface.summarize_geometry` and the readers of `scripts/build_national_vulnerability_anchors.py`); the receipt records that their SHA-256 and the input SHA-256 values equal those in the anchor receipt. The national table of 7,425 units was not computed again.

**What the range is.** The plan gives a range for residents inside a flood input, [known, known + unsupported] (plan 1.3, MVP-02), and no formula for how the 1 km cell size moves a tambon's share. The table shows the two allocation extremes so that effect can be seen. It is not a confidence interval, and the owners have not decided whether or how it enters the vulnerability component.

**What the run shows about the age grid.** These are properties of the input, read from the rasters over the district's bounding box (99.81–100.04 E, 20.25–20.47 N); no value for a tambon was computed for them.

- The age composition hardly varies inside the district. Of the 544 cells with a count in that box, 378 (84,342 of 116,786 modelled residents) have a dependent share of 0.40555, to within 0.00006. Another 120 cells sit as close to 0.40678 or 0.44091, and 46 cells (18,529 residents) carry other values. Across Thailand, 436,874 of the 488,637 populated cells fall in groups of 20 or more cells whose share is the same to six decimal places. This looks like one age composition per district, applied to every cell of the district; it was not checked against the district polygons. A tambon's share is then close to its district's share, and the differences between tambons come mostly from edge cells.
- In all eight tambons the cells wholly inside the tambon give the same share, 0.405551. The area-weighted shares of five tambons lie between 0.4055 and 0.4056. The other three differ because of edge cells with another composition. The largest of those cells holds about 7,078 residents at a share of 0.3516 and lies on the northern border (99.883–99.892 E, 20.450–20.458 N).
- No cell with a valid count in that box has zero residents. The rasters are the constrained product, so a cell with no count is most likely a cell with no mapped settlement. The table still reports such area as unsupported, with no count, as the plan asks: unknown, not zero. It is 18.7 of the 305.6 km² of the eight tambons, and between 0 and 15.3 percent of a tambon.
