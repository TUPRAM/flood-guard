# outputs/planning_v1

Small committed outputs of the planning overlay (restructuring plan v2, section 3.1). The first table lists the receipts of the engineering runs made for protocol v1b before it was signed, including the run of record of the corridor and the E4 build of record. None of those files holds an FPPS, an A–E class, an ensemble or a value for a single tambon. Protocol v1b was signed and recorded on 3 October 2026 (`docs/proposal_execution/RECEIPTS.jsonl`); the runs made since then are in the second table, under "Runs made with protocol v1b in force". The owners answered every owner choice on 3 October 2026 (decision log R12); the status column says which receipt that turned into evidence of record. A review the same day reopened OI-04 and OI-06 of protocol v1b: the join log and the facility counts of the run of record were measured by the E0 spike, and those two items take their values from task E4 (owner-choices entry 1, plan row G7b). In R13 the owners chose to wait for E4 (entry 24, option A); the E4 build of record reproduced the spike's values exactly, and both items closed from it. A file written before R12 is not rewritten, so its own `status` field may still say `candidate`; protocol v1b says what it is now. The planning-frame build of 3 October names tambons, so its receipt sits beside the frames in `resources/planning_frames/`, not here.

**Every file** carries `generated_at_utc`, `source_timestamp`, `confidence_class` (always `low`), `confidence_basis`, `assumptions`, `official_warning: false` and `operational_status: non_operational`. In a JSON file they are at the top level; in a GeoJSON file they are in the feature's properties. A candidate file also carries `status: candidate` inside the file, and a file of the run of record carries `status: of_record` (`log_of_record` for the join log, `run_of_record` for the receipt), so a copy taken out of this folder still says what it is. `tests/test_planning_v1_outputs.py` checks all of this for every file here. None of these outputs is an official warning or an observation of a flood.

The facility table and the context hold DDPM rows (pitch level), so they stay outside Git under `<external_data_workspace>/proposal_execution/planning_v1/<case>/e4_<mode>/`; a candidate build writes all its files there and nothing here. `--verify` rebuilds into a temporary folder and compares byte for byte the join log, the facility table, the receipt without its `run` section and the retained context, whose build time (`generated_at`) alone is left out. Each spike file carries its generation time, so its SHA-256 changes from run to run. To compare two runs, use the hashes of the content alone: `geometry_sha256` in a corridor file, `joins_sha256` in a join log and `context.canonical_sha256` in a spike receipt. The `reproducibility` block of a spike receipt does that comparison against the run before it.

The inputs are read-only files outside Git. Their locations are arguments of each script, and their SHA-256 values are in each receipt. The owner decisions are in `docs/proposal_execution/planning_protocol_v1b_owner_choices.md`, answered on 3 October 2026 as recommended (decision log R12).

**What the ranking measured, for the whole frame.** 26,130 of the 65,673 baseline edges (65,328 road edges and 345 grade-join connectors) carry a baseline route. 99.6% of the residents with a route reach a main-road entry before a hospital, so trunk and primary edges carry no flow and are not ranked. The 20 highest-ranked links are 20 consecutive edges of one tertiary street (OSM way 1114870832), with 8,722 to 9,261 residents each. The top 200 lie on five OSM ways and include two grade-join connectors (ranks 163 and 164).

**What the protocol leaves open** (`open_points` in the receipt; nothing below is decided by the script):

- **E6-OP5, graph bridges.** The rule says "Add graph bridges (Tarjan) to cover the all-routes-lost case" and not what they are added to (the ranked set, the 200 edges of the full reroute or the 20 of the output) or where a bridge stands against a link ranked by flow. Nothing is added: a bridge is flagged and ranked by its flow. The graph has 23,311 graph bridges and 8,317 of them are ranked; none is among the top 200, and the best-ranked one is at rank 1,473 with 371 residents. Removing an edge that is not a graph bridge leaves every node connected, so closing any single top-20 link on its own isolates nobody. Class rule v2 trigger B closes on its own a top-20 link that intersects the flood extent and counts the residents who lose every route, so it can only fire through a top-20 link that is a graph bridge.
- **E6-OP1, grade-join connectors.** The protocol ranks edges and does not say whether a connector can be a critical link. 168 connectors are ranked. 163 of them carry exactly the flow of a road edge and are ranked ahead of it, because a connector ID sorts before a road edge ID (90 of them directly ahead). The run stops for a connector among the top 20; there is none. In one of the 13 units that hold a ranked link, a connector is among the three highest-ranked links of the unit, which scenario S3 reads from the same table.
- **E6-OP6, a later run of the ranking.** The protocol does not say whether a run that supersedes the first run may change the recorded ranking. An answer to E6-OP1 or E6-OP5 may change the table, so both are needed before a later task uses its SHA-256.
- **E6-OP7, a zero-minute edge between two destinations.** The route is carried across it to the destination with the smaller ID, as the comparison of `select_interventions` does. 40 destination nodes are routed onward this way, and they carry no resident.
- **E6-OP2, E6-OP3, E6-OP4.** What the full reroute of the top 200 writes (none was run); whether the bridge flag is the graph bridge or the OSM tag (both are written); the unit of a link whose midpoint lies in no unit or in more than one (none occurred).

- **E10-OP7, people losing 30-minute access.** The protocol names no service; both public services are reported at 30 minutes. EED and EER are plan task E9.
- **E10-OP8, where the access tables of the minus and plus levels go.** They are in the file outside Git of each case. Those of case SE1 have a public lineage of their own, as the committed E5 table has; the owners say whether they are committed (E1-OP1, E8-OP7).
- **E10-OP9, one at a time.** The protocol does not say from which cell an item is varied; the two flood anchors are applied to the default cell alone.
- **E10-OP10, counts that state a value of a single tambon.** The receipts hold, for each cell that was run, the number of tambons in each class, and name no tambon beside a value. Those counts state values of single tambons all the same: for case O2 the class of every tambon in every cell, and for case SE1 the same, through the one tambon that alone is class B and the cells whose counts differ from the default cell (see the two cases above). Unlike the rows of task E8, the class of a tambon in a cell of the minus or plus flood level cannot be rebuilt from the other committed files. Guardrail GR6 speaks of an overlay and of `apps/web/public/`; nothing says whether such a count may stand in a committed receipt when the lineage is below the public level. The owners say whether it may. If not, `class_counts_by_cell` and every sentence that follows a single tambon through the cells leave the receipts and this file and are kept in the file outside Git only; what is in the Git history since commit `b9ecf25` stays there unless the owners decide otherwise.
- **E10-OP11, the cells retention is taken over for a result that is not a public overlay.** Protocol v1b states the 180 cells of the public facility set "for a public overlay". The results of this task are not an overlay and their publication eligibility is `local`. A run at the public level reads the public facility set only and takes its 180 cells as the set of the rule; should all 180 have a class one day, the rule would be evaluated over them. Every record gives the same counts and bounds over the 540 core cells beside it, and no status is set from either today. The owners say which set applies.
- **E10-OP12, the levels declared cut line 6 would keep.** The cut reads "Population-vintage and vulnerability-anchor axes (540 to 135 cells)" and does not say which level of each axis stays. The share after the cut is given with the levels of the default cell kept (WorldPop 2020, P10 / P90) and, beside it, for every other pair of levels whose cells were all run (today: WorldPop 2020 with P5 / P95). The owners say which levels stay when the cut is invoked.
